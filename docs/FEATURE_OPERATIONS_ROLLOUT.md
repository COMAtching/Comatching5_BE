# 중간 위험 수정 배포와 운영 스위치

## 배포 순서

1. [인증 세션 전환](AUTH_SESSION_ROLLOUT.md)을 마친 환경에서 [기능 상태 테이블](../db/migrations/20261123_02_feature_operation.sql)을 `comatching_user`에, [주문 수량 열](../db/migrations/20261123_03_purchase_order_quantity.sql)을 `comatching_item`에 적용한다. 두 스크립트는 재실행할 수 있다. 기존 주문의 `product_quantity`는 NULL로 둔다. 당시 일반 상품은 주문 건수, 할인 매칭권은 주문에 포함된 티켓 수로 한도를 계산했기 때문이다.
2. 사용자 서비스를 처음 띄우기 전에 `OPERATIONS_INITIALLY_CLOSED`를 확인한다. 값은 닫을 기능 키를 쉼표로 나열한다. AWS 기본값은 `LOGIN,MATCHING,SHOP_PAYMENT`이고 로컬 기본값은 빈 값이다. 최초 생성되는 행에만 적용되며 재시작 후에는 관리자가 저장한 값이 유지된다. 기존 환경의 운영 시간과 다르면 최초 기동 전에 명시한다.
3. 게이트웨이·사용자·채팅·아이템·알림 서비스의 `INTERNAL_SERVICE_TOKEN`을 같은 값으로 설정한다. 게이트웨이와 사용자 서비스에서 쓰던 Redis 세션 저장소를 채팅·아이템·알림에서도 사용한다. 세션 검사에 필요한 Lua 명령과 `INFO server`, `INFO replication`을 각 서비스 계정으로 확인한다. 매칭·채팅·아이템에서 사용자 서비스의 운영 상태 조회 주소가 올바른지 확인한다.
4. 이미지 저장소는 앱 출처의 multipart `POST`를 CORS에서 허용한다. 서버 역할에는 `s3:ListBucket`과 관리할 경로의 `s3:GetObject`, `s3:PutObject`, `s3:DeleteObject`가 필요하다. `pending-uploads/`는 공개 읽기를 차단하고 정식 프로필·채팅 경로의 기존 읽기 정책을 유지한다. 버전 관리 버킷은 임시 경로의 비현재 버전 수명도 확인한다.
5. 사용자 서비스를 먼저 준비한 뒤 게이트웨이·매칭·채팅·아이템·알림 서비스를 교체한다. 인증·주문·업로드 요청이 구 버전으로 흘러가지 않도록 기존 인스턴스를 드레인한다. 마지막으로 프런트엔드와 서비스 워커를 배포하고 열린 탭을 새로고침한다. 이때 운영 콘솔의 **기능 운영** 메뉴를 사용한다. 구형 가입 화면은 작성 세션 표식을 보내지 못하므로 새로고침한 뒤 다시 작성한다. 구 버전이 이미 발급한 이미지 PUT 서명은 발급 후 최대 5분까지 유효하다.

## 운영 화면과 서버 동작

운영자는 `/adminpage/operations`에서 기능별로 종료·재개하고 이용자 안내 문구를 저장한다. 화면에는 최근 변경자·시간이 표시된다. 두 운영자가 같은 버전에서 저장하면 먼저 반영된 변경을 유지하고 뒤의 요청에는 409를 반환한다.

| 기능 키 | 종료 시 사용자 요청 | 종료 중에도 가능한 작업 |
| --- | --- | --- |
| `LOGIN` (전체 서비스) | 접속 중인 일반·가입 진행 회원의 모든 기기를 로그아웃시키고 로그인·가입·복구·조회·채팅·매칭·구매 등 회원 이용을 중단 | 관리자 콘솔 로그인·갱신·운영 업무, 공개 운영 상태 조회 |
| `CHAT` | 메시지 전송, 새 첨부, 실시간 수신, 읽음 갱신, 채팅 푸시 | 참여 중인 방의 기존 대화와 첨부 조회 |
| `MATCHING` | 신규 매칭. 이용권 차감 전에 검사 | 기존 매칭 내역 조회 |
| `SHOP_PAYMENT` | 상품 구매 화면과 신규 주문 | 기존 주문 조회, 관리자 승인·지급·환불 |

전체 서비스의 저장 키는 기존 `LOGIN`을 사용한다. 이 키가 이미 닫혀 있으면 새 버전 기동 시 기존 일반 회원 세션도 폐기한다. 재개하면 이전 개별 설정을 다시 적용하며 회원은 새로 로그인한다. 채팅 단독 종료 시에는 기존 대화를 읽을 수 있지만 전체 종료 중에는 대화 조회도 중단된다. 운영 작업과 이미 접수된 주문의 정산은 계속된다.

세션 형식을 함께 사용하는 게이트웨이·사용자·채팅·아이템·알림 인스턴스는 구버전 트래픽을 드레인한 뒤 함께 전환한다. 대규모 회원 DB에서는 전체 종료 시 회원 ID를 512개씩 조회해 Redis에 일괄 폐기하므로 운영 전 테스트 환경에서 소요 시간을 확인한다. 전체 종료 완료 후 재개·재로그인까지 확인한 뒤 운영에 적용한다.

사용자 서비스는 `/api/public/operations`에 공개 스냅샷을, `/api/public/operations/stream`에 SSE 변경 알림을 제공한다. 프록시에서 이 경로의 응답 버퍼링과 캐시를 끄고 지속 연결을 허용한다. 탭은 다시 연결하거나 포커스를 되찾을 때 상태를 갱신한다. 서버는 각 보호 작업 전에 저장된 상태를 확인한다. 종료 상태는 409 `FEATURE_CLOSED`, 상태를 확인할 수 없는 경우에는 503이다. 관리자 API는 `/api/v1/admin/operations`에 있다.

## 배포 확인

- 두 기기에서 같은 회원으로 로그인한 다음 한쪽을 로그아웃한다. 그 기기의 열린 소켓과 푸시 등록이 끊기고 다른 기기의 채팅이 유지되는지 확인한다. 같은 브라우저에서 다른 계정으로 로그인한 뒤 새 계정의 채팅 목록만 열리는지도 확인한다. 구형 단일 FCM 토큰은 새 클라이언트가 정상 세션으로 설치 등록을 마친 뒤 새 방식으로 발송한다. 이미 외부 제공자에 전달된 알림은 서버에서 회수할 수 없다.
- 관리자와 이용자를 서로 다른 브라우저에 띄우고 전체 서비스 종료 뒤 두 기기의 일반 세션이 만료되고 관리자 콘솔을 계속 쓸 수 있는지 확인한다. 재개 후 다시 로그인하고 세 개별 기능을 하나씩 종료·재개한다. 채팅 단독 종료 시 채팅방은 이전 대화를 유지하고, 매칭권·새 주문은 종료 시 변하지 않아야 한다. 상점 종료 전에 접수한 주문은 운영자 화면에서 계속 처리한다.
- 인증 메일은 성공한 발송 후 60초가 지나면 재발송할 수 있다. 새 코드의 유효시간은 5분이다. 기본 발송 한도는 수신자별 시간당 6회, 출처별 10분당 120회, 전체 분당 120회이며 초과 시 429와 `Retry-After`를 반환한다. 프록시를 경유한다면 `COMATCHING_MAIL_TRUSTED_PROXIES`에 실제 신뢰하는 프록시 CIDR만 지정한다. 기본값에서는 직접 연결한 피어의 IP를 사용한다.
- 프로필 10 MiB, 채팅 20 MiB 파일과 1바이트 초과 파일로 저장소 정책을 확인한다. 발급은 회원당 기본 시간당 30회(`comatching.uploads.hourly-limit`), 서명은 5분, 업로드 후 첨부 가능 시간은 2시간이다. 사용자·채팅 서비스는 24시간이 지난 임시 객체와 사용하지 않는 복사본을 매시간 정리한다. 정식 경로가 참조된 이미지는 보존한다. 복사에는 원본 ETag 일치와 목적지 키 부재 조건을 함께 적용한다.
