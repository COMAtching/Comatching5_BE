# 인증 세션 전환 배포

채팅 프로필은 채팅방 목록의 공개 방향을 따른다. A가 B를 차단하면 A의 상세 조회만 중단된다. 가입 확인과 계정 생성은 같은 브라우저의 30분짜리 일회용 HttpOnly 쿠키를 사용한다.

## 배포 순서

1. 채팅 서비스를 배포하고 채팅방 참여자 쌍 인덱스 `chat_room_participants` 생성을 확인한다.
2. 운영 기본 설정은 Hibernate 스키마 검증이다. 사용자 서비스 교체 전에 [인증 버전 마이그레이션](../db/migrations/20261123_01_member_auth_version.sql)을 적용한다. 기존 회원의 초기 버전은 0이다.
3. 점검 중 가입·로그인·보호 API 트래픽을 멈추고 사용자 서비스, 게이트웨이, 프론트엔드를 함께 교체한다. 구형 인스턴스를 드레인한 뒤 트래픽을 연다. 기존 토큰은 모두 한 번 다시 로그인해야 한다. 가입 인증만 끝낸 사용자는 이메일을 다시 인증한다.
4. 일반·카카오·관리자 로그인, 온보딩 직후 역할과 닉네임, 두 기기의 비밀번호 복구·탈퇴, 관리자 로그아웃 후 회원 조회와 재발급을 확인한다. 프론트엔드와 API가 운영 쿠키 도메인을 공유하는지 확인한다. 액세스 경로는 `/`, 리프레시는 `/api/auth`다.

## 운영 및 복구

- 새 기기에서 로그인하면 최신 기기만 갱신할 수 있다. 이전 기기의 액세스는 만료까지 허용한다. 개별 로그아웃은 같은 로그인에서 발급한 토큰들을 종료한다.
- Redis 연결 장애 시 보호 요청과 세션 발급·폐기는 실패한다. 세션은 로그인 당시 Redis 주 노드의 프로세스 ID(`run_id`)와 복제 이력 ID(`master_replid`)에 묶인다. 재시작, 다른 주 노드로 전환, 기존 노드 재승격 시 과거 스냅샷에 남은 세션도 재로그인해야 한다. 배포 전 사용자 서비스와 게이트웨이가 주 노드에 연결되고, 두 서비스 계정이 Lua에서 `INFO server`와 `INFO replication`을 읽을 수 있는지 확인한다. Redis를 재시작하지 않고 과거 데이터를 덮어쓰는 수동 복구라면 보호 트래픽을 닫고 사용자 서비스와 게이트웨이의 JWT 서명 키를 함께 교체한 후 재개한다.
- 롤백 시에도 구형 토큰을 다시 허용하는 게이트웨이에 트래픽을 보내지 않는다. 두 서비스의 세션 계약이 일치하는 버전을 배포하고 인증이 확인된 뒤 점검을 해제한다.
- 기존 성능 테스트용 오프라인 JWT 생성기와 과거 토큰 CSV는 활성 서버 세션을 만들지 않는다. 새 시험에는 전용 테스트 계정의 정상 로그인으로 발급한 세션이 필요하다.
- 여기서 세션 종료는 이후 HTTP 요청·재발급·신규 연결에 적용된다. 이미 열린 WebSocket과 오프라인 PWA 문서 캐시는 별도의 수명 관리 대상이다.
