# 거래내역 수집 검증 기록

## 2026-11-25 · 0.5.4 KB 자동 조회 3분 복원

모의 Chrome 알람으로 로컬·운영의 3분 예약과 시작 후 180초·360초 조회를 확인했다. 활성 상태로 남아 있는 30초 예약을 복구할 때 첫 조회를 3분 뒤로 설정하고 구버전 알람을 무시했다. 독립 Chrome 합성 화면을 포함한 확장 테스트 31개가 통과했다.

## 2026-11-25 · 0.5.3 서비스 워커의 완료 보고 재전송

독립 Chrome 서비스 워커와 루프백 합성 수신기로 0.5.2의 상태 보고 및 완료 전송에서 Illegal invocation을 재현했다. 0.5.3의 기본 fetch로 전환하고 토큰을 다시 연결하자 상태 보고가 성공했다. 기존 대기 회차의 같은 scanId가 접수됐고, 이미 접수된 입금 행의 추가 전송 없이 대기함이 비고 체크포인트가 갱신됐다.

## 2026-11-25 · 0.5.2 빠른조회 하단의 다음 버튼

사용자가 보여 준 두 종류의 KB 표 하단을 합성 HTML로 재현했다. 독립 Chrome에서 건수·페이지 번호 없이 6건·7원인 단일 표와, 단독 다음 버튼이 있는 세 페이지에서 같은 결과를 확인했다. 페이지 교체·누적 추가·누적 재렌더링, 표 안과 밖의 버튼을 검증했다. 다른 영역의 다음 버튼은 누르지 않았고, 버튼 중복과 이동 중 바뀐 행은 보류했다. 확장 테스트 31개 및 번호 없는 회차의 Spring 수신 → 임베디드 Kafka → 주문 승인 통합 테스트가 통과했다. 실계좌에 수정판을 적용한 결과는 별도 확인이 필요하다.

## 2026-11-25 · 0.5.1 로컬 30초 조회

0.4.0은 Node 테스트 21개와 임시 H2·Kafka 통합 테스트를 사용한다. 같은 1,000원 입금 2건과 출금 1건을 합성해서 실제 확장 송신 함수로 HTTP 요청 후, Kafka에서 입금 2건의 키·JSON을 확인했다. 서버 응답 유실과 불완전한 접수 응답, 재시작 후 토큰 재입력, HTTP 충돌 묶음 보류, Kafka 송신 실패 후 발행 복구를 검증했다. Kafka ACK 후 DB 완료 표식이 유실된 상황을 재현했을 때 같은 eventId로 재발행됐다.

## 2026-11-24 · 동명이인 입금 처리 방침

KB 수취 계좌 하나와 상품 정가를 유지한다. 고객은 평소 사용하는 입금자명으로 한 번 송금한다.

한 입금에 이름과 결제 금액이 일치하는 주문이 둘 이상이면 입금과 후보 주문 전체를 운영자 확인 대상으로 남긴다. 같은 이름의 1,000원 주문 3건에 1,000원 입금이 3건 들어와도 자동 승인은 0건이다. 한 사람이 두 번 송금했을 수 있으므로 건수나 도착 순서로 주문을 배정하지 않는다.

운영자가 이체 내역을 대조해 확인한 입금 한 건만 주문 한 건에 연결한다. 후보 일부가 취소·만료되거나 수동 승인되어 한 건만 남아도, 이미 충돌한 나머지 입금은 계속 확인 대상으로 둔다.

0.4.0 당시에는 수집기와 주문별 관리자 승인 기능이 독립적으로 동작했다. 미확인 입금과 후보 주문을 함께 보관하고 표시하는 기능은 0.5.0에서 추가했다. 기존 주문에는 만료 정책이 적용된다.

## 2026-11-23 · 토스 송금 링크의 주문코드 전달 검증

사용자가 서로 다른 주문코드를 `message`에 넣은 테스트 링크로 1원씩 두 번 송금한 후 KB 빠른조회 원본 표를 확인했다. 두 입금 모두 `내통장표시내용`은 빈칸이고 `의뢰인/수취인`에는 같은 이름이 표시됐다. 두 입금은 거래일시와 잔액으로 구분되지만, 어느 입금이 어느 주문에 해당하는지 식별할 코드는 두 행 모두에 없었다.

이번에 확인한 토스 송금 경로에서는 `message`를 자동 승인의 근거로 사용할 수 없다. 이름과 금액이 같은 주문이 겹치면 입금 순서로 배정하지 않고 확인 대상으로 남긴다.

## 2026-11-23 · KB 빠른조회 실화면, 확장 0.2.2

Chrome에 로드된 작업 폴더의 확장을 0.2.2로 갱신하고 같은 빠른조회 결과 탭에서 **거래내역 읽기**를 실행했다. 한 거래의 두 행을 각각 제외하던 0.2.1에서 정상 0건·확인 필요 2행이었고, 수정 후 정상 1건·확인 필요 0행으로 원본의 입금 건수와 합계가 일치했다. 이 확인은 해당 페이지의 수동 읽기에 한한다.

## 미검증

- 실제 Chrome 확장 로드 및 activeTab 권한에 의한 은행 프레임 주입.
- KB 계정의 토스뱅크 연결, 타행 거래내역 제공 여부.

사용자는 이 Mac에 은행 보안 프로그램 설치를 원하지 않으며 다른 PC에서 실계좌 검증을 진행할 예정입니다. 이 환경에서 로그인·계좌 연결·보안 프로그램 설치를 진행하지 않았습니다.
